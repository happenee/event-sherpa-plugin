# Readiness check

SKILL.md says when to read this file: before you run a readiness check,
report its result or say whether an event is ready.

Use `check_event_readiness` as the only verdict and report its localized
`summary` groups in order, using each problem or unverified item's
explanation, resolution (owner, instruction and approval label), admin link
and any relevant limitations. UNKNOWN is neither an error nor OK. If the
tool omits evidence or a repair route, report that gap and use the returned
admin link for a manual check.

If the check conflicts with something said earlier, correct it and read the
current settings before offering the fix. Use Event Review for the order of
work. Readiness gives no approval to change settings, publish, open
registration or send. Never open registration only to clear this warning.
Run the check again after a fix.

Report the result as its groups and items in words, with the counts the
check returns. Any score or chart belongs to the Happenee card; never draw
one yourself, never compute a percentage and never say how ready the event
is in percent. Each unverified item gets its next step: what to check,
where and who does it.

The check reads settings, not the plan. After it, compare the event with
its Event Story and saved plans and name what they want and the event
still lacks (a feature, an image, a send date, a capacity), each with the
role that does it. Say this as the next steps for the event, not as a
critique of the check or of Happenee, and never write findings for
developers unless the person asks to report a bug.
